Document de conception — firmware Lwip_demo_H753

1. Objet et périmètre

Ce document s'adresse aux développeurs qui reprennent ou font évoluer le firmware de la carte STM32H753ZI (Nucleo-144) qui pilote les régulateurs LDO. Il est généré par Doxygen à partir des commentaires du code : toute fonction documentée dans Core/Src/main.c y apparaît automatiquement avec son rôle, ses paramètres, sa valeur de retour et un exemple d'utilisation. Les chapitres 1 à 9 (ce fichier, Doxygen/conception.dox) décrivent la conception d'ensemble ; la suite décrit chaque fonction, module par module.

Périmètre : Core/Src/main.c, Core/Inc/main.h, l'en-tête généré Core/Inc/ldo_config_genere.h et les scripts Python de configurationLDO/. Les pilotes HAL, LwIP et FreeRTOS fournis par ST ne sont pas décrits.

2.2 Séquence de démarrage

  1. main() (code CubeMX) : caches, HAL_Init(), horloges, déblocage des bus I2C (I2C_BusRecovery()), MX_GPIO_Init() et périphériques, puis LDO_GPIO_Init() qui configure les broches des LDO à partir de ldoConfig[].
  2. Création de la tâche lwipTask (StartLwipTask()) et démarrage de FreeRTOS.
  3. StartLwipTask() : LwIP, verrous (CreerMutexI2C(), CreerMutexUART(), CreerMutexCommandes()), réception UART, LDO_InitialiserTables(), OC_InitialiserSeuilsDefaut(), InitialiserConfigDacsI2C1(), DAC_RestaurerMemoire(), DAC_ConfigurerSeuilsPotentiometre(), CmdOnOff_Initialiser(), MX_OC_EXTI_Init(), udpServer_init(), sortCommandTable().

2.3 Boucle principale

Une seule tâche applicative. À chaque tour de la boucle de StartLwipTask() :

  1. LDO_MettreAJour() pour chaque LDO : lecture OC (avant l'écriture de EN), verrouillage éventuel, écriture EN / BLD, lecture PG ;
  2. OC_SignalerEvenements() : une ligne OC_TRIP:<nom>:... par nouveau défaut ;
  3. rafraîchissement des puces DAC (tableDac[]), sauf puces I2C2 si i2c2_actif = 0 et sauf puce en cours de balayage ;
  4. boutons : capture complète (ExecuterCaptureComplete()), reset des multiplexeurs ;
  5. SurveillerConfigDacsI2C1(), DAC_TraiterSauvegardes() (EEPROM), CmdOnOff_TraiterSauvegarde() (flash) ;
  6. UART1_TraiterCommande() : commande UART en attente ;
  7. battement de cœur HB sur l'UART.

Les commandes UDP sont traitées dans le contexte LwIP (udp_receive_callback()) ; les deux chemins appellent tc_request() sous le verrou des commandes.

Le câblage des LDO n'est écrit ni dans main.c ni dans le .ioc : il est décrit par configurationLDO/ldo_config.csv, une ligne par LDO, l'ordre des lignes donnant l'index (0 à LDO_NB-1).

  • LDO_GPIO_Init() configure les broches à partir de ldoConfig[] (le .ioc ne contient plus que la configuration système) ;

5. Protection de surintensité (OC)

Pour une LDO protection = LM211, la sortie du LM211 arrive sur la broche OC.

  1. Masquage : pendant OC_BLANKING_MS (10 ms) après la mise à 1 de EN, l'OC est ignoré (soft-start).
  2. Déclenchement : OC actif et protection armée → OC_Verrouiller() : EN coupé, défaut verrouillé, bleeder forcé, compteur incrémenté. Si oc_interruption = 1, la coupure est faite dans l'interruption EXTI (OC_SurFrontIT()), en quelques microsecondes.
  3. Signalement : OC_SignalerEvenements() émet OC_TRIP:<nom>:... sur l'UART.
  4. Réarmement : RST_BL_LDO_<nom> (LDO_RelacherBleeder()) ou RST_OC_LDO_<nom> (OC_Rearmer()), refusé tant que la broche OC signale encore la surintensité.
  5. Verrous : SET_EN_LDO_<nom> est refusé tant que le défaut est verrouillé (REFUS_OC_VERROUILLE) ou que le bleeder est actif (REFUS_BLEEDER_ACTIF).

Seuil : code DAC de 410 à 4006 (0,19 à 1,90 A), 1056 (0,50 A) au démarrage. Seuil (A) = code × 5 V / 4096 / 2,61 V/A, hors hystérésis. CMD_ON_OFF_OC = 0 neutralise la surveillance (LED grise côté IHM).

6. Persistance

6.1 Codes DAC en EEPROM du MCP47FEB28

Pour une LDO memoire = EEPROM : après chaque modification, DAC_DemanderSauvegarde() programme une écriture différée ; DAC_TraiterSauvegardes() écrit le registre non volatil (10h-17h, tWC = 16 ms max) ; au démarrage DAC_RestaurerMemoire() relit ces valeurs.

6.2 Commandes ON/OFF en flash interne

  • Zone : banque 2, secteur 7, 0x081E0000, 128 Ko, réservée dans STM32H753ZITX_FLASH.ld (FLASH LENGTH = 1920K) ;
  • enregistrements de 64 octets écrits à la suite : magic "CMD1", LDO_CONFIG_CRC32, numéro de séquence, LDO_NB, masques BLD et OC, CRC32 ;
  • CmdOnOff_Initialiser() retient le dernier enregistrement valide de même empreinte ; sinon valeurs du CSV (CMD_ON_OFF_BLD, CMD_ON_OFF_OC) ;
  • CmdOnOff_TraiterSauvegarde() regroupe les bascules (500 ms) ; le secteur n'est effacé que lorsqu'il est plein (environ toutes les 2048 sauvegardes).

7. Concurrence et interruptions

Ressource Protection Règle
hi2c1, hi2c2 un mutex par bus (CreerMutexI2C(), ResoudreMutexI2C()) Toute transaction I2C hors interruption prend le mutex du bus
USART1 en émission mutex UART (UART1_EnvoyerTexte()) Jamais d'émission depuis une interruption
last_message, response verrou des commandes (Commande_Verrouiller()) tc_request() n'est jamais exécuté deux fois en parallèle
Interruptions EXTI — Positionnent un drapeau ; seule exception : coupure OC (OC_SurFrontIT())
Réception UART — HAL_UART_RxCpltCallback() n'appelle aucune API FreeRTOS

8. Faire évoluer le firmware

8.1 Ajouter ou recâbler une LDO

  1. Modifier configurationLDO/ldo_config.csv (ou la page /dac/config du contrôleur) ;
  2. compiler dans CubeIDE (le pre-build régénère les fichiers) et flasher ;
  3. vérifier GET_CONFIG_LDO : l'empreinte doit être celle du CSV du contrôleur.

Aucune ligne de main.c n'est à modifier.

8.2 Ajouter une commande fixe

  1. Écrire le gestionnaire static void h_MA_COMMANDE(void), qui lit ses paramètres dans last_message (strsep(&last_message, ":")) et écrit sa réponse dans response ;
  2. le documenter (modèle du chapitre 9, avec @ingroup) ;
  3. ajouter { "MA_COMMANDE", h_MA_COMMANDE } dans commandTable[] (ordre indifférent : la table est triée au démarrage) ;
  4. déclarer le prototype dans la zone USER CODE BEGIN PFP.

8.3 Ajouter une commande par LDO

Ajouter une branche else if (strncmp(token, "PREFIXE_", n) == 0 && (idx = findLdoIndex(token + n)) != -1) dans tc_request(), avant les branches de préfixes plus courts qui pourraient la masquer.

8.4 Régénération CubeMX

Tout le code applicatif est dans des zones USER CODE BEGIN / END. Les commentaires des fonctions générées par CubeMX (main(), MX_*_Init()…) sont réécrits à chaque génération : leur documentation est donc dans Doxygen/complements_cubemx.dox.

9. Convention de commentaire

Chaque fonction est précédée d'un bloc Doxygen en français :

/**
  * @brief  Ce que fait la fonction, en une ou deux phrases.
  * @param  idx  Index de la LDO (0 a NB_LDO-1).
  * @retval uint8_t  1 si ..., 0 sinon.
  * @par    Exemple d'utilisation
  * @code
  * if (OC_EstSurveillee(idx) != 0U) { ... }
  * @endcode
  * @ingroup grp_oc
  */

Une fonction sans paramètre porte @param Aucun., une fonction void porte @retval Aucun (void).. L'exemple est toujours encadré par @code / @endcode et @ingroup range la fonction dans son module (liste des modules à la fin de Doxygen/conception.dox).

Le document Word de conception est produit par Doxygen/generer_doc_conception.bat (Doxygen puis doxygen_vers_docx.py) : voir la notice Doxygen du projet.
